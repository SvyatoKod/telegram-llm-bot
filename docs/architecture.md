## Архитектура проекта

Проект — Telegram-бот, который принимает текстовые сообщения, хранит историю диалога **в памяти** и отправляет контекст в LLM (Ollama) для генерации ответов.

### Основные компоненты

- **`src/index.js`**: точка входа. Загружает `.env`, читает конфиг, создаёт клиентов и запускает long-polling Telegram.
- **`src/telegram/telegramPoller.js`**: опрашивает Telegram updates (long-poll).
- **`src/handlers/textMessageHandler.js`**: бизнес-логика обработки сообщений.
  - поддержка команды `/clear`
  - сбор обязательного контекста (system prompt + история)
  - сжатие истории (summary), если она превышает лимит
  - логирование полного контекста, который уходит в модель
- **`src/services/dialogHistoryService.js`**: in-memory хранилище истории по `userId` (Telegram `msg.from.id`).
- **`src/llm/ollamaClient.js`**: клиент Ollama.
  - основной режим: `/api/chat` с массивом `messages: [{role, content}, ...]`

### Поток обработки сообщения

1. Telegram poller получает update с текстовым сообщением.
2. `TextMessageHandler` извлекает `userId` и `chatId`.
3. Если текст равен `/clear`, история пользователя очищается и бот отвечает подтверждением.
4. Иначе:
   - сообщение пользователя добавляется в историю,
   - если история стала слишком длинной, запускается **процедура саммари** (см. ниже),
   - формируется массив `messages` для LLM: **system prompt** (если задан) + история диалога,
   - полный контекст и примерный размер в токенах пишутся в лог,
   - отправляется запрос в Ollama `/api/chat`,
   - ответ сохраняется в историю и отправляется в Telegram.

## Ограничения и особенности

### Хранение истории

- **Только в памяти**: история теряется при перезапуске процесса.
- **Отдельно для каждого пользователя**: ключ — `userId` (Telegram `from.id`).

### Ограничение размера истории (COUNT_MESSAGE_LIMIT)

- История обрезается по количеству сообщений (user/assistant суммарно).
- При превышении лимита удаляются **самые старые** сообщения.
- В файл логов пишется событие `history_trim` с причиной `COUNT_MESSAGE_LIMIT`.

### Сжатие контекста (саммари) (COUNT_MESSAGE_SUMMARY_LIMIT)

Если сообщений в истории больше, чем `COUNT_MESSAGE_SUMMARY_LIMIT`, выполняется сжатие:

- “Старая часть” диалога отправляется в LLM с запросом на краткое резюме.
- История заменяется на:
  - одно сообщение-резюме в начале (`Резюме предыдущего диалога: ...`)
  - + небольшой “хвост” последних сообщений (чтобы сохранить ближайший контекст)
- В файл логов пишутся события `summary_start` и `summary_done`.

### System prompt как обязательный контекст

- `SYSTEM_PROMPT` всегда вставляется первым сообщением `role: "system"` перед отправкой в модель.

### Логирование контекста LLM

- Перед каждым вызовом модели полный входной контекст логируется в `logs/llm-context-YYYY-MM-DD.log`.
- Формат файла — JSON-строки (одна запись на строку). Внутри есть `messages` и `approxTokens` (приближённая оценка).
